## Context

当前候选分组由 `CleanupCandidate.source` 的中文字符串推断 provider，provider 行的可点击状态和候选列表分组分别在两个视图中计算。扫描说明则挂在每个 provider 行下方，即使只有当前运行项可见，也会为多个行保留说明空间。

## Goals / Non-Goals

**Goals:**

- 让扫描说明在 provider 面板标题下方集中显示为单行，超出可用宽度时循环滚动。
- 让四类候选从创建时就拥有稳定的 `CleanupProvider` 身份。
- 让候选分组、provider 可点击状态和滚动锚点复用同一 provider 身份。
- 修复应用残留和空间分析等后部候选分组的可靠定位，同时保留 320 至 640 的滚动区域约束。

**Non-Goals:**

- 不改变四类 provider 的扫描范围、候选筛选规则或清理安全边界。
- 不改变候选具体来源文案、候选排序或选中规则。
- 不新增 tooltip、弹层或圆球下方的独立提示行。

## Decisions

### 1. 候选身份使用 typed provider

为 `CleanupCandidate` 增加 `provider: CleanupProvider`，所有候选创建入口显式传入四类 provider。`source` 保留为具体来源或诊断信息，但不再承担分组、可点击判断、锚点或清理安全判断。

这比继续维护中文字符串映射更可靠：展示文案可以调整，候选身份和锚点不会随之变化；同时四类 provider 使用完全一致的数据流。

### 2. 分组和锚点使用同一 provider ID

候选区按 `candidate.provider` 聚合，顶部可点击集合从相同的候选分组身份产生，分组标题使用 `provider.title` 展示。每个 `ForEach` 元素保持单一稳定的分组容器，滚动目标直接使用 `CleanupProvider` 作为 ID，并绑定在分组容器上。候选分组数量受滚动区域限制，使用普通 `VStack` 一次性完成锚点布局，再安排到下一轮主线程后滚动到目标中心，避免较后分组受 `LazyVStack` 延迟布局影响。

只有候选复核列表已经挂载时，provider 行才可点击；如果列表挂载前已经产生了目标，则在列表 `onAppear` 时补执行滚动，避免目标在扫描阶段被提前消费。

### 3. 说明放在 provider 面板标题下方

provider 面板标题行只显示“扫描进度”，下方使用固定单行说明槽显示当前运行 provider 的范围，文案统一以“正在”开头。标题、说明和 provider 行使用一致的垂直间距，provider 行设置统一的最小行高，让信息保持紧凑但有足够呼吸感。provider 行左侧图标表达完成、进行中或异常状态，右侧只保留数量和大小，不重复显示状态文字。短文案静态显示，超出可用宽度时以固定间距连续循环滚动；扫描开始或 provider 切换时只替换这一个文本槽，扫描完成后将其透明度和高度收拢。启用减少动态效果时不启动跑马灯，改为单行截断。provider 行恢复为单行状态，不再为每个行保留说明占位。

### 4. 扫描中实时更新 provider 数量

扫描服务在发现候选时发送 `candidateDiscovered` 事件，ViewModel 将事件追加到当前扫描结果，并递增对应 provider 的候选数量和已知大小。provider 完成时仍使用最终 `ScanResult` 覆盖统计，确保扫描中显示的是实时值，完成后显示的是最终值。

## Risks / Trade-offs

- **[候选模型新增必填身份会影响现有初始化]** → 搜索并更新全部 `CleanupCandidate` 构造路径，编译器负责暴露遗漏。
- **[候选分组较多会增加一次性布局成本]** → 仅分组容器改为一次性布局，候选数量受固定滚动区域约束，换取四类锚点的稳定性。
- **[说明文案长度不一]** → 使用固定单行槽，超长文案循环滚动，扫描完成后通过动画收拢。
