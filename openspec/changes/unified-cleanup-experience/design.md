## Context

当前实现已经收敛为固定主界面：`MenuBarView` 只负责主容器和阶段分发，`CleanerViewModel` 负责会话状态，`CleanerService` 负责 provider 扫描、候选校验和执行。安装包、启动磁盘文件和目录、Time Machine 在同一个大文件扫描 provider 中完成，结果也在主界面原位呈现。

## Goals / Non-Goals

**Goals:**

- 用一个主状态容器承载 idle、scanning、awaitingConfirmation、applying 和 result 状态。
- 一次扫描覆盖所有清理 provider，扫描结束后统一进入确认阶段。
- 保留现有启动磁盘、权限、照片图库排除、Time Machine 和废纸篓安全边界。
- 对已卸载应用残留、安装包、大文件、项目构建产物和项目依赖提供可解释的候选分组。
- 使用圆形一键清理按钮、单一阶段提示和低干扰状态动画。

**Non-Goals:**

- 不扫描或清理外部、网络或可移动磁盘。
- 不把系统应用、共享应用数据或无法确认归属的残留加入可选清理候选。
- 不将 `node_modules` 按大小阈值筛选，也不展示其内部文件。
- 不在本次变更中增加重复文件分析、可视化磁盘树或后台定时清理。

## Decisions

### 1. 使用统一清理会话和 provider 编排

保留 `CleanerService` 作为底层文件与命令执行入口，在其上增加统一扫描会话。会话按 provider 产出结构化扫描事件和候选，不再让 `startQuickClean()` 单独拼接两个 category。

Provider 逻辑分为：

- 深度清理：白名单缓存、旧日志和可验证的刷新操作。
- 应用残留：只检查用户目录中与已卸载应用高置信关联的残留。
- 项目：构建产物、工具缓存和项目依赖。
- 大文件扫描：合并检查用户位置内的 DMG、PKG、MPKG 等安装包、启动磁盘全盘文件和目录，以及 Time Machine 状态；不设置 200 MB 体积阈值，快照维护操作单独确认。

各 provider 依次运行并发布阶段事件，避免多个全盘遍历同时争用 I/O；每个 provider 都有完成、部分、跳过和失败状态。

### 2. 扫描、选择和执行严格分离

扫描只产生不可变候选快照，不得调用任何删除或管理员命令。候选统一保存在结果状态中：

- 已知安全、边界明确的缓存和旧日志可以默认勾选，但仍必须等待最终确认。
- 应用、残留、大文件扫描候选、项目依赖和 Time Machine 维护默认不勾选。
- 选中或取消只更新内存中的选择状态，候选始终留在列表中。

用户点击“确认移到废纸篓”后，界面先显示明确的确认提示；只有用户再次确认，ViewModel 才创建 `CleanupPlan` 并交给执行器。执行器只接收确认后的计划，重新校验路径、大小、保护状态和移除模式。

### 3. `node_modules` 采用路径发现、聚合体积计算

项目遍历发现名为 `node_modules` 的目录后，先检查父级项目的 `package.json`、支持的 lock 文件、符号链接状态和 `lsof` 使用状态，然后跳过该目录的子树，不枚举内部候选文件。

候选可以异步计算整体体积，但体积不参与筛选，没有大小阈值。界面只显示聚合体积和完整路径；候选默认未选中，确认后整体移入废纸篓。

### 4. 应用残留采用高置信归属

以已安装应用的 Bundle ID 作为内部比对信息，只用于排除仍在使用的应用数据，不将应用本体加入候选。用户目录下无法在已安装应用中找到对应 Bundle ID 的 Application Support、Preferences、Caches、Containers 和 Saved Application State 路径，才作为已卸载应用残留候选。共享目录、系统应用和无法确认归属的路径只做诊断，不进入候选。

### 5. 固定主界面骨架

使用一个始终存在的主清理容器承载所有阶段，不能只是在同一个 popover 中切换多套页面：

```text
固定标题与磁盘信息
  └─ idle: 圆形“一键清理”按钮
       └─ scanning: 原位显示当前 provider 与运动中的圆形按钮
            └─ awaitingConfirmation: 原位显示候选、选择和确认操作
                 └─ applying: 原位显示清理进度与取消
                      └─ result: 原位显示释放空间、分组结果和未处理候选
```

标题、启动磁盘和可用空间在所有阶段保持不变；阶段内容只在主界面内部原位变化，不进入独立页面。按钮在 idle 状态使用 macOS 系统蓝，显示白色单色橡皮擦图标和“一键清理”；悬停时只显示一段短暂的白色边缘、整体轻微抬升，按下时轻微回弹；scanning/applying 状态不显示额外 loading，圆形主按钮保留橡皮擦图标和当前阶段文字，并通过缓入缓出的放大、回落、轻微抬升和倾斜表达工作状态；scanning 阶段只有 provider 日志中处于“检查中”的条目使用循环箭头图标并持续顺时针旋转，其他状态图标保持静止，进入 applying 阶段后停止旋转；扫描完成进入 awaitingConfirmation 后，圆形主按钮显示检查完成和静态确认图标，停止呼吸与位移动效，provider 日志保持在圆形按钮下方，并在每个 provider 行显示可测量的候选体积，候选结果和确认操作继续排在日志下方；result 状态显示成功标记、释放空间和分组结果。权限受限时使用“需要完全磁盘访问”和“开启后，扫描结果会更完整”两行简短文案，并保持单行显示；右侧“去设置”仅保留文字，和刷新操作一起使用统一高度、紧凑间距的固定操作组。所有可用的按钮在悬停时显示手形指针，禁用操作不显示手形指针。候选区域采用中性玻璃面板，标题栏与滚动内容明确分隔，避免浅蓝底色与高饱和链接同时占据大面积；每项只保留单行路径与体积，路径默认使用中性文字，过长时使用中间省略，悬停通过系统提示显示完整路径。分组标题只承担分类和数量汇总作用，具体项目区域按内容自然展开并设置合理最大高度，超出后滚动；确认移除与取消操作固定在候选区域下方并列展示，主次按钮保持明显对比。仅保留按压反馈、整体主按钮运动、检查日志图标旋转和完成过渡，并在减少动态效果设置下关闭持续动画；减少动态效果设置下不显示悬停边缘反馈和抬升。

候选区的确认操作不使用两端对齐，两个按钮按内容宽度紧凑居中排列，避免操作距离过大破坏视觉关联。

### 6. 启动磁盘扫描继续采用安全边界

启动磁盘 provider 只以 `/` 为本地边界，跳过外部、网络、可移除和系统受保护路径。媒体隐私边界由统一的排除前缀和目录名过滤器维护，当前至少覆盖用户的 `Pictures`、`Music`、Photos/Music 资料库、所有应用包、`Music.app` 以及 Apple Music 的容器、偏好和保存状态；所有目录读取、属性读取、递归和体积计算都必须先经过该过滤器。应用残留 provider 需要读取应用包的 Bundle ID，但该读取只用于归属判断，不把应用包加入大文件候选，也不递归进入应用包内容。通过路径过滤后才读取条目元数据，后续判断复用同一批属性，避免重复访问文件系统；取消和超时检查按小批次执行，避免为每个条目重复加锁和取当前时间。扫描完成后才汇总候选，不使用固定遍历上限提前结束；候选展示限制只能作为 UI 分页或排序限制，并明确标记扫描是否完整。

### 7. 所有文件删除统一进入废纸篓

所有文件、目录、应用、残留、安装包、项目依赖和大文件候选都使用 Trash 路由。普通用户路径调用 `FileManager.trashItem`；系统缓存和旧日志等需要管理员权限的候选使用受校验的 `mv` 操作放入当前用户的 `.Trash`。模型不再提供永久删除模式。

Time Machine 快照维护是系统级维护命令，不是文件删除，继续使用独立的管理员确认和结果类型。

### 8. 使用确认计划作为唯一执行入口

所有实际动作都生成带类别、路径、移除模式和终态的结果。`CleanupPlan` 保存用户确认时的候选快照和选择集合；执行器不接受扫描结果直接执行。用户文件、应用、残留、安装包、项目依赖和大文件进入废纸篓；需要权限的系统操作单独批量授权。执行前重新验证路径、大小（可获得时）、符号链接、保护状态和移除模式。

## Risks / Trade-offs

- **[全盘扫描耗时较长]** → provider 分阶段显示进度，允许取消，并保留已完成 provider 的结果。
- **[应用残留归属可能不准确]** → 只将高置信匹配作为候选，所有歧义路径保持保护状态。
- **[`node_modules` 体积统计仍需遍历内部]** → 只为聚合体积执行一次异步统计，不产生子项、不用于阈值筛选，用户可在统计完成前看到路径候选。
- **[用户确认后候选发生变化]** → 执行器只接收确认时的不可变 `CleanupPlan`，执行前逐项重新校验，变化项单独失败且不影响其他项目。
- **[刷新服务可能影响用户进程]** → 仅实现命名且有边界的刷新操作，拒绝任意进程终止和无界系统变更。

## Migration Plan

1. `CleanerService.scanProvider` 和 `scanUnified` 只负责读取、计算和产出候选。
2. `CleanerViewModel` 在扫描完成后进入 `awaitingConfirmation`，不启动执行器。
3. 结果区域保留所有候选，选择状态不改变候选可见性。
4. 确认提示通过后创建 `CleanupPlan`，执行器才允许移动项目到废纸篓。
5. 每次代码或界面修改后执行 Debug 构建、测试，并关闭旧实例后启动新构建产物。
