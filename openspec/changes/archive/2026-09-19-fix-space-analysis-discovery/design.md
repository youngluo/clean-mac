## Context

当前空间分析从 `/` 开始深度遍历，并在遍历过程中才判断候选路径。启动磁盘上的受保护目录、TCC 限制和大量条目可能消耗整个分析时间窗口，使标准目录中的候选尚未被处理。路径排除还混合了通用媒体目录、媒体库后缀和系统应用数据，导致用户可清理文件被跳过。

架构结论（评审确认）：统一扫描为"3 段定向扫描 + 1 段带子树记忆化的全盘遍历"。前序 provider 完整聚合的子树注册进扫描上下文并被空间分析复用，昂贵的大小读取对每个目录至多发生一次；唯一轻量二次枚举是项目搜索根的名称预扫。重复候选展示由前置归属屏蔽与最终所有权去重共同保证。本 change 以"更快 + 无重复展示"为目标，不引入单次遍历重写。

## Goals / Non-Goals

**Goals:**

- 让标准目录中的大文件在有限扫描时间内稳定进入候选。
- 只保护系统 Photos/Music 应用及明确关联的数据，保留其它用户媒体目录的正常扫描。
- 在扫描前建立可靠的卷边界和系统保护边界。
- 对硬链接和元数据读取失败做可解释、可重复的处理。
- 保持现有候选排序、大小显示和数量；部分完成但已有候选的空间分析状态使用成功勾选表达可用结果。

**Non-Goals:**

- 不增加空间概览展示或候选数量限制。
- 不把普通大目录转换为候选项。
- 不改变应用残留、缓存或 Time Machine 的扫描规则；项目产物仅收紧候选判定（见决策 7），不改扫描根与近期保护。
- 不修改 SwiftUI 文案、布局或候选列表结构；仅调整 provider 状态图标和颜色的判断。

## Decisions

### 1. 标准目录优先，启动磁盘统计继续保留

扫描队列先处理存在且位于启动卷的 `Downloads`、`Desktop`、`Documents`，再处理其它启动卷目录。目录被重复遇到时复用已收集的指标，避免优先扫描造成重复计数或重复候选。这样不需要缩短全盘分析范围，也不会依赖候选数量截断来掩盖超时问题。

备选方案是只扫描三个标准目录，但会使空间统计失真；或增加更高的全盘超时，但会继续受慢目录影响，因此不采用。

### 2. 媒体保护改为明确的应用关联路径

取消对用户 `Pictures`、`Music`、`Movies` 根目录的通用排除。路径分类仍会在读取元数据前执行，但只保护系统 Photos.app、Music.app 和可明确归属于它们的应用容器、图库或资料库路径；普通用户媒体文件按标准目录候选规则处理。通用 `.app` 保护继续生效，避免把其它应用包当作普通文件扫描。

备选方案是继续排除所有媒体目录，安全但会隐藏用户下载或手工保存的大文件；或允许进入 Photos/Music 应用包，风险过高，因此不采用。

验证阶段发现通用 `.app` 后缀按组件名排除过宽：`Library/Application Support/com.example.app` 这类 bundle-ID 命名的应用数据目录被整树跳过，其中安装包不再进入候选。最终约束：`.app` 后缀仅在名称去掉后缀后不构成 bundle ID（非多段点分隔）时才视为应用包排除；bundle-ID 风格目录照常参与统计与候选评估。

### 3. 使用卷身份而不是路径前缀判断启动卷

启动卷扫描先取得根目录卷身份，进入目录和文件时比较实际卷身份，并继续跳过符号链接。`/Volumes`、`/Network` 以及其它挂载卷不进入启动卷分析，即使它们在路径上位于遍历树中也不能绕过边界。

### 4. 统一硬链接去重和尺寸读取

在一次启动卷分析中使用文件资源身份去重已经统计和候选化的文件；没有资源身份时以标准化路径作为保守回退。候选仍使用当前展示的分配大小，普通文件阈值仍使用逻辑大小判断，不改变界面上的数值含义。元数据读取失败会标记部分扫描并记录诊断，不再静默跳过。

### 5. 保护系统目录但不扩大用户目录保护

从 `/` 开始遍历时，`System`、`bin`、`sbin`、`usr`、`etc`、`private/var` 等系统运行目录在递归前直接作为受保护范围处理；用户目录仍可进入空间分析，标准目录不因位于用户目录而被保护。保护项目只进入已有的内部空间统计，不生成可选候选。

### 6. 前序 provider 的实际候选拥有路径优先

统一扫描按缓存清理、项目清理、应用残留、空间分析的顺序执行。空间分析只根据前三个 provider 已实际生成的候选路径屏蔽自身候选；如果候选是目录，则屏蔽其子项，避免同一内容重复展示。空间分析仍继续遍历这些路径并计入空间统计，前序 provider 因近期修改、归属不明确或读取失败没有生成候选时，空间分析可以继续发现其中符合规则的大文件或特殊文件。

单独调用空间分析时没有前序 provider 候选上下文，因此不额外屏蔽缓存、项目或应用路径，仍使用自身的路径和安全规则。统一扫描最终仍通过候选所有权优先级处理其它重叠候选。

### 7. 项目产物候选要求名称与项目标记双条件

本应用面向通用用户，`build`、`dist`、`target`、`venv` 等产物目录名会命中普通用户资料目录（如 `~/Documents/素材/build`）。名称命中仅是嫌疑：从产物目录的父目录起向上探测直到该次扫描根，祖先链中存在任一项目特征标记（`.git`、`package.json`、`go.mod`、`Cargo.toml`、`pyproject.toml`、`Podfile`、`Gemfile`、`composer.json`、`pom.xml`、`build.gradle`/`build.gradle.kts`、`*.xcodeproj`、`CMakeLists.txt`）才生成候选，否则视为普通目录丢弃。向上探测而非只看父目录，以兼容 monorepo 中层级较深的产物目录。扫描根（含 `~/Documents`）、30 天近期保护和聚合、注册逻辑保持不变；标记探测为每嫌疑目录若干次 stat 级检查，开销可忽略。

备选方案是将 `Documents` 移出扫描根，但会丢失开发者将项目放在 `Documents` 下的覆盖，且闸门生效后该风险本身已消除，因此不采用。

## Risks / Trade-offs

- [Risk] 全盘统计仍可能因权限或超时不完整 → 优先完成标准目录，并保留已有 partial 和不可读取诊断。
- [Risk] 媒体应用数据路径随 macOS 版本变化 → 使用系统应用包路径、稳定 Bundle ID 容器和明确资料库后缀的组合，未知路径不因名称猜测为保护对象。
- [Risk] 硬链接去重可能减少看似重复的候选 → 同一文件身份只能清理一次，避免清理确认后的体积和实际文件不一致。
- [Risk] 卷身份属性不可用 → 回退到现有路径边界（`/Volumes`、`/Network` 前缀判断），不额外标记部分完成；实测 firmlink 下 `/` 与 `/Users` 返回相同 `volumeIdentifier`，回退路径极少触发。
- [Risk] 已提交进仓库的输出目录（如站点 `dist/`）同时满足名称与标记条件 → 保持默认不选中、trash 移除模式和确认流程托底。
- [Risk] 无标记的手工 `build/` 目录不再成为候选 → 接受漏报优于误伤通用用户资料目录。

## Migration Plan

无需数据迁移。升级后下一次统一扫描使用新的空间分析规则，已有清理历史和用户选择不变。
