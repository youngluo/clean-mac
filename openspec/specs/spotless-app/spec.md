# spotless-app 规范

## Purpose

Spotless 提供一条聚焦的菜单栏清理流程，用于检查启动磁盘并展示需要用户确认的清理候选项，不暴露多个相互竞争的入口。
## Requirements
### Requirement: 统一清理扫描范围

应用 SHALL 从一键清理主操作启动一次统一扫描，覆盖深度清理、应用清单及残留、缓存与服务刷新机会、项目产物，以及合并后的空间分析（安装包、压缩包、指定目录中的大文件和 Time Machine 状态）。

#### Scenario: 完成一键扫描

- **WHEN** 用户启动一键清理
- **THEN** 应用检查统一扫描中的每个启用 provider
- **AND** 报告每个 provider 已完成、已跳过、部分完成或失败
- **AND** 不要求用户单独进入空间分析入口

#### Scenario: 安全候选项和复核候选项

- **WHEN** 统一扫描发现候选项
- **THEN** 明确安全的候选项可以默认选中，但不会执行
- **AND** 应用、应用残留、项目依赖和大文件扫描候选项保持待复核状态

### Requirement: 统一清理扫描性能

统一清理 SHALL 在保证缓存、项目产物、应用残留和空间分析覆盖范围的前提下，尽量复用同一次目录和文件属性读取。目录候选 SHALL 在一次聚合遍历中同时得到实际分配空间、逻辑大小和扫描完整性；空间分析 SHALL 复用已经完整扫描的目录，不得因复用而遗漏适用的安装包、压缩包或普通大文件规则。

#### Scenario: 目录聚合一次完成

- **WHEN** provider 计算目录候选的体积
- **THEN** 一次遍历同时计算实际分配空间和逻辑文件大小
- **AND** 候选展示和清理汇总使用实际分配空间
- **AND** 清理前复核可以使用同一次聚合产生的逻辑大小快照

#### Scenario: 空间分析复用完整扫描目录

- **WHEN** 空间分析遍历到本次统一扫描中已经完整读取的缓存、项目产物或残留目录
- **THEN** 应用复用该目录的聚合统计并跳过重复递归
- **AND** 将复用的实际分配空间合并到启动磁盘统计
- **AND** 首次遍历中适用的空间分析候选观察项仍然进入统一候选集合

#### Scenario: 不完整目录继续补扫

- **WHEN** 已有 provider 因取消、超时、权限错误、读取失败或入口限制未完整读取目录
- **THEN** 应用不得将该目录标记为可复用边界
- **AND** 空间分析继续尝试读取该目录并保留部分完成或不可用诊断

#### Scenario: 父目录候选保持唯一归属

- **WHEN** 已完整扫描的父目录已经作为缓存、项目产物或残留候选覆盖其子树
- **THEN** 空间分析不再为同一子树创建重复文件候选
- **AND** 父目录的实际占用空间只计入一次
- **AND** 未被父目录候选覆盖的相邻目录继续参与全局空间分析

#### Scenario: 未归属目录保持全局发现

- **WHEN** 文件位于未被其他 provider 完整扫描的允许用户目录
- **THEN** 空间分析继续识别全局安装包和压缩包
- **AND** 继续识别 `~/Downloads`、`~/Desktop`、`~/Documents` 中逻辑大小超过 10 MB 的普通文件

#### Scenario: 缓存扫描不承担无效观察开销

- **WHEN** provider 聚合位于 `Library` 下的缓存或应用残留目录
- **THEN** provider 只读取创建目录候选所需的实际占用、逻辑大小和文件身份信息
- **AND** 不收集空间分析观察项或读取观察项专用的修改时间
- **AND** 项目产物等允许空间分析的目录继续收集安装包、压缩包和普通大文件观察项

#### Scenario: 临时文件扫描不执行外部占用检查

- **WHEN** 缓存清理扫描临时目录中的候选文件
- **THEN** 应用不得启动 `lsof` 或其它逐文件占用检查进程
- **AND** 应用依据文件类型、修改时间、所有者和符号链接状态筛选候选
- **AND** 临时文件只有在超过 15 天未修改时才进入候选
- **AND** 清理前重新校验文件身份、实际大小和逻辑大小，内容发生变化时跳过

#### Scenario: 当前用户临时文件使用系统废纸篓

- **WHEN** 缓存清理发现当前用户拥有的临时文件
- **THEN** 应用通过系统废纸篓 API 移动文件，不为该文件启动管理员特权命令
- **AND** 只有真正需要系统权限的缓存、日志或 Time Machine 操作才使用清理会话的管理员授权

### Requirement: 候选列表使用可确认的清理单元

应用 SHALL 以用户可确认的清理单元展示候选项。一个清理单元可以代表一个文件或目录，也可以代表同一临时根目录下经过筛选的多个文件；候选列表不得因临时文件数量增长而逐文件无限展开。

#### Scenario: 临时文件按根目录聚合

- **WHEN** 同一配置临时根目录下存在多个符合条件的临时文件
- **THEN** 应用只展示一个代表该根目录的候选组
- **AND** 候选组展示内部文件数量、聚合实际占用空间和根目录路径
- **AND** 候选组默认不选中

#### Scenario: 用户旧日志不进入快速清理

- **WHEN** 统一扫描发现 `~/Library/Logs` 或 `/private/var/log` 下的旧日志
- **THEN** 快速清理不创建对应候选项
- **AND** Codex Desktop 等诊断日志不进入默认清理范围

#### Scenario: 临时文件候选清理

- **WHEN** 用户确认一个临时文件候选组
- **THEN** 应用逐个复核并处理候选组内部文件
- **AND** 不删除或移动临时根目录本身
- **AND** 单个文件变化、消失或校验失败时不影响其它内部文件的独立处理

#### Scenario: 临时文件组部分完成

- **WHEN** 一个临时文件候选组内至少一个文件处理成功，且另有文件被跳过或失败
- **THEN** 候选组结果标记为部分完成
- **AND** 保留导致跳过或失败的首个诊断信息

#### Scenario: 清理结果页不提供重新扫描入口

- **WHEN** 候选确认、清理完成或部分完成状态显示底部操作区
- **THEN** 操作区只提供当前状态需要的清理操作和“完成”操作
- **AND** 不显示“重新扫描”按钮
- **AND** 用户点击“完成”返回空闲页后，可从主清理入口重新开始统一扫描

### Requirement: 快照未知值保持保守

应用 SHALL 在临时文件缺少修改时间时跳过该文件；临时文件聚合只有在至少一个目标的实际大小或逻辑大小已知时才报告对应聚合值，未知值不得按零计入。

#### Scenario: 临时文件部分完成影响空间

- **WHEN** 临时文件候选组中部分目标成功移入废纸篓，其他目标失败或被跳过
- **THEN** 结果标记为部分完成
- **AND** 结果影响空间只包含已成功处理目标的已知大小

### Requirement: 单界面清理交互

应用 SHALL 在同一个主弹出面板中呈现空闲、扫描中、等待确认、清理中和结果状态。状态变化 SHALL 更新当前界面内容，不应跳转到独立的清理、分析或完成页面。

#### Scenario: 统一进度界面

- **WHEN** 用户启动统一扫描或清理
- **THEN** 同一界面显示当前阶段、进度和取消控制
- **AND** 只使用一个主要阶段提示，不额外叠加 loading
- **AND** 扫描时在圆球下方显示一条当前阶段短语，provider 区域显示当前 provider 和已扫描数量

#### Scenario: 圆形主操作反馈

- **WHEN** 用户将鼠标移到“一键清理”圆形按钮上或按下按钮
- **THEN** 按钮使用主题品牌色 `#3FA796`，仅显示白色阶段文案、短暂的白色边缘和轻微的抬升、回弹反馈
- **AND** 用户启动扫描后，圆形按钮通过整体轻微呼吸、抬升和倾斜表达当前工作状态，不额外显示 loading
- **AND** 扫描阶段日志中处于“扫描中”的 provider 使用循环箭头图标并持续旋转，进入清理阶段后停止旋转
- **AND** 开启减少动态效果时不显示扫描呼吸动画

#### Scenario: 检查完成仍留在主界面

- **WHEN** 统一扫描完成并进入等待确认
- **THEN** 同一主界面的圆形按钮显示“扫描完成”文案，不显示图标
- **AND** 圆形按钮停止呼吸、抬升和倾斜动效
- **AND** provider 日志位于圆形按钮下方，候选结果和确认操作位于日志下方
- **AND** 圆球下方的扫描阶段提示在进入等待确认后隐藏
- **AND** provider 分类列表在扫描完成后显示“已完成”状态
- **AND** provider 和可清理项目分组统一使用“缓存清理”“项目清理”“应用残留”“空间分析”名称
- **AND** 有对应候选分组的 provider 行可点击，并将候选列表滚动到同名分组标题；没有对应候选分组的 provider 行不可点击
- **AND** 扫描完成后的 provider 行和候选分组使用紧凑的垂直间距，状态切换不发生瞬间跳变
- **AND** provider 日志在有可测量数据时显示对应候选体积
- **AND** 大文件扫描有候选但没有可测量体积时显示“大小未知”

#### Scenario: 等待确认

- **WHEN** 只读扫描完成
- **THEN** 同一界面保留所有可处理候选项
- **AND** 选择变化不会把候选项从列表中移除
- **AND** 每个候选项展示单行路径，过长路径使用末尾省略，悬停可查看完整路径
- **AND** 候选区标题展示“可清理项目”、已选数量和已选项目的总大小
- **AND** 每个候选项上侧展示名称和可测量体积，下侧展示单行路径，分类汇总由分组标题承担
- **AND** 分组标题与候选区顶部内容保持一致的水平边距
- **AND** 具体项目列表的可滚动区域最小高度为 320，最大高度为 640，超出最大高度后滚动
- **AND** 候选分组之间使用紧凑留白，不绘制可见横向分隔线，provider 跳转使用稳定的分组标识定位到对应分组
- **AND** 每个 provider 锚点包含一致的顶部留白，首个“缓存清理”分组滚动后不贴近候选标题栏
- **AND** 分组默认展示和锚点滚动后的顶部留白保持一致
- **AND** 候选标题栏与具体项目列表保持清晰分隔，路径默认使用中性文字，交互时使用主题强调色
- **AND** 路径仅用于识别候选位置，不提供打开路径操作
- **AND** “移到废纸篓”和“取消”按钮在候选列表下方按内容宽度紧凑居中并列展示
- **AND** 候选项使用紧凑的圆形复选框
- **AND** 不移动或删除任何文件和目录

#### Scenario: 直接移到废纸篓

- **WHEN** 用户点击“移到废纸篓”
- **THEN** 应用开始执行清理操作
- **AND** 选中的文件和目录通过 macOS 废纸篓处理

#### Scenario: 执行前取消

- **WHEN** 用户在执行前点击“取消”
- **THEN** 应用返回候选项列表
- **AND** 不改变任何文件或目录

#### Scenario: 清理完成仍留在主界面

- **WHEN** 扫描或确认后的清理完成
- **THEN** 同一界面显示圆形按钮文案“清理完成”以及“可清理项目”列表
- **AND** 已处理候选项直接在原列表行显示“已移到废纸篓”“已清理”“失败”等状态
- **AND** 不显示独立的清理前后空间汇总、统计卡片或清理结果明细列表
- **AND** 仍未处理的候选项继续留在列表中，用户可以不离开该界面继续选择和确认

#### Scenario: 语言一致性

- **WHEN** 用户在右键菜单中选择应用语言
- **THEN** 主界面和右键菜单使用同一语言显示
- **AND** 扫描、清理或结果处理进行中不允许切换语言
- **AND** 语言切换不会改变当前清理候选项或文件系统状态
- **AND** 应用生成的扫描、诊断和清理结果消息在展示时按当前应用语言解析
- **AND** 未分类的系统或外部命令原文不被本地化层改写

### Requirement: 已卸载应用残留

应用 SHALL 只把能够高置信度确认属于已卸载应用的数据加入“应用残留”候选。扫描 SHALL 建立当前应用身份目录，覆盖 `/Applications`、`/System/Applications`、`~/Applications`、Homebrew Cask、Setapp、输入法、运行应用、按 Bundle ID 查询的 LaunchServices 注册应用和用户/系统启动项，并递归收集应用包内的嵌套 Helper、Service、Updater、Extension 等 Bundle。Bundle ID、签名应用标识（包含 Team ID）和应用组 SHALL 进入身份索引；应用来源扫描 SHALL 在进入 Bundle 包后停止展开包内资源，避免把资源目录误判为应用来源缺失。应用发现不完整或身份读取失败时 SHALL 暂停应用残留候选判定。Bundle ID 相同或以已安装 Bundle ID 加点号作为前缀的数据不得进入候选。`Library/Caches`、`Library/Containers` 和 `Library/WebKit` 下仅凭目录名无法确认归属的数据视为不明确项，不进入可选择候选。

#### Scenario: 已卸载应用残留分组

- **WHEN** 扫描发现用户目录中的数据无法与当前已安装应用关联
- **THEN** 应用只将高置信度的残留作为复核分组展示
- **AND** 不将任何已安装应用本体加入清理候选项

#### Scenario: 不明确的应用残留

- **WHEN** 残留路径无法高置信度关联到某个应用
- **THEN** 应用将其标记为信息项或受保护项
- **AND** 不将该路径加入可选择清理集合

#### Scenario: 已安装应用后缀归一化

- **WHEN** Preferences 或 Saved Application State 中的项目名以 `.plist` 或 `.savedState` 结尾
- **THEN** 应用在比对已安装 Bundle ID 前去掉该后缀
- **AND** 与已安装应用匹配的数据不进入残留候选

#### Scenario: 当前应用组件不作为残留

- **WHEN** 应用残留扫描发现的 Bundle ID 属于已安装应用，或属于其嵌套组件、启动项或 Bundle ID 子命名空间
- **THEN** 应用不创建对应的应用残留候选

#### Scenario: 归属不明确的数据不作为残留

- **WHEN** `Library/Caches`、`Library/Containers` 或 `Library/WebKit` 下存在看起来像 Bundle ID、但无法确认已卸载的数据
- **THEN** 应用不将该路径加入可选择候选
- **AND** 不因“未在顶层 `.app` 中找到同名 Bundle ID”就认定应用已经卸载

#### Scenario: 应用发现不完整时暂停残留判定

- **WHEN** 任一已存在的应用来源目录无法读取，或应用发现因取消而未完成
- **THEN** 应用残留 provider 报告部分扫描
- **AND** 本次扫描不生成应用残留候选

#### Scenario: 多来源应用保护数据

- **WHEN** Bundle ID 对应的应用位于 Homebrew Cask、Setapp、系统应用目录、用户输入法目录或其它已发现的应用来源
- **THEN** 应用将其视为当前应用身份
- **AND** 该身份及其嵌套组件对应的数据不进入应用残留候选

#### Scenario: 已卸载应用的身份数据仍可复核

- **WHEN** Preferences、Saved Application State、HTTPStorages、Application Scripts 或 Application Support 下的 Bundle ID 曾在应用仍存在时被身份历史确认
- **AND** 该 Bundle ID 的所有历史拥有者都不在当前完整身份目录中
- **THEN** 应用可以将该路径作为待复核的应用残留候选
- **AND** 候选默认不选中

#### Scenario: 孤立启动项不阻止残留识别

- **WHEN** LaunchAgent 或 LaunchDaemon 只剩 `Label`、`BundleIdentifier` 或 `AssociatedBundleIdentifiers`，但对应应用包、可执行文件和 LaunchServices 注册均不存在
- **THEN** 应用不得仅凭这些字段把该身份加入当前应用目录
- **AND** 已有历史归属且其它拥有者均已消失的数据仍可作为待复核残留

#### Scenario: 应用身份读取失败时保持安全

- **WHEN** 已注册应用的 Bundle、嵌套组件或代码签名信息无法读取
- **THEN** 应用残留 provider 报告部分扫描
- **AND** 本次扫描不生成应用残留候选

### Requirement: 安装包和压缩包发现

应用 SHALL 在当前用户目录内识别允许位置的安装包和压缩包，不因其位于 `~/Library` 或不在常用下载目录而漏检。保护目录、诊断日志目录、排除目录、符号链接和非当前用户目录仍不得产生候选；安装包和压缩包不受固定体积阈值限制，普通非安装包文件仍只在 `~/Downloads`、`~/Desktop`、`~/Documents` 中按 10 MB 逻辑大小阈值识别。

#### Scenario: 安装包和压缩包候选项

- **WHEN** 扫描在非保护位置发现 DMG、PKG、MPKG、XIP、IPSW、ZIP、RAR、7Z、TAR、GZ、BZ2、XZ 或其他配置的安装包和压缩包
- **THEN** 应用报告其路径和可测量体积，并作为待复核候选项展示
- **AND** 在明确确认前不移除该文件

#### Scenario: Library 中的安装包

- **WHEN** `~/Library` 下未落入保护或诊断日志边界的位置存在 `.dmg`、`.pkg`、`.mpkg`、`.xip`、`.ipsw`、`.zip`、`.rar`、`.7z`、`.tar.gz`、`.tgz` 等文件
- **THEN** 空间分析将其作为待复核候选展示
- **AND** 清理前校验使用与扫描相同的允许路径边界

#### Scenario: 常用目录普通大文件

- **WHEN** 扫描在 `~/Downloads`、`~/Desktop` 或 `~/Documents` 发现非安装包和非压缩包的普通文件且其体积大于 10 MB（10,000,000 字节）
- **THEN** 应用将其并入“空间分析”分组并报告路径和可测量体积
- **AND** 该候选项保持待复核状态

#### Scenario: 普通文件规则不扩张

- **WHEN** `~/Library` 或其它非标准大文件目录存在超过 10 MB 的普通文件
- **THEN** 该文件不会仅因体积超过阈值进入空间分析

#### Scenario: 候选体积使用实际占用空间

- **WHEN** 扫描文件或目录候选项并计算可释放体积
- **THEN** 应用优先报告文件系统实际分配的空间，而不是直接使用逻辑文件大小
- **AND** 对目录聚合体积去重硬链接文件，避免重复计入同一份已分配空间
- **AND** 清理前同时复核实际分配空间和逻辑文件大小的变化

### Requirement: 缓存和服务刷新

应用 SHALL 将缓存刷新和服务刷新表示为范围受限且名称明确的操作，并分别报告结果。一次清理不得终止无关用户进程或执行范围不受限的系统修改。缓存清理 SHALL 只将当前用户拥有、超过 15 天未修改的普通非符号链接文件加入临时文件候选组，并按配置临时根目录聚合展示；扫描阶段不得启动 `lsof` 或其它逐文件占用检查进程。

#### Scenario: 范围受限的刷新操作

- **WHEN** 存在已配置的缓存或服务刷新操作
- **THEN** 应用只在文档规定的范围内执行该操作
- **AND** 分别报告成功、跳过、失败或权限受限

#### Scenario: 不安全的刷新操作

- **WHEN** 刷新操作需要终止无关进程或改变范围不受限的系统状态
- **THEN** 应用跳过该操作
- **AND** 解释跳过原因，不将统一清理整体标记为失败

#### Scenario: 全局开发工具缓存分类

- **WHEN** 扫描发现 npm、pnpm、pip、Homebrew、Xcode 或其他已配置开发工具的全局缓存
- **THEN** 应用将其归入“缓存清理”而不是“项目清理”
- **AND** 该候选默认不选中并显示聚合体积
- **AND** 自定义缓存路径不扩大到用户目录之外

#### Scenario: 多个临时目录缓存分类

- **WHEN** 扫描发现 `/private/tmp`、`/private/var/tmp`、`/var/tmp`、`/tmp` 或当前进程临时目录下超过 15 天未修改的普通文件
- **THEN** 应用将其归入“缓存清理”而不是“空间分析”
- **AND** 该候选默认不选中，并通过系统废纸篓 API 移到用户废纸篓，不额外请求管理员权限
- **AND** 应用跳过符号链接、目录、特殊文件和非当前用户拥有的文件
- **AND** 清理前重新校验文件身份、实际大小和逻辑大小，扫描后发生变化的文件不执行清理
- **AND** 清理逐个处理候选组内文件，不删除或移动临时根目录本身

#### Scenario: 临时文件缺少修改时间

- **WHEN** 临时目录中的普通文件无法读取修改时间
- **THEN** 应用跳过该文件，不将其加入候选组

#### Scenario: 临时目录安全边界

- **WHEN** 扫描缓存和空间候选
- **THEN** 应用不递归扫描整个 `/private/var/folders`，只处理当前进程 `TMPDIR` 指向的具体目录
- **AND** 不自动处理近期修改的临时文件

### Requirement: 项目依赖安全

应用 SHALL 将 `node_modules` 视为项目依赖候选项，而不是通用缓存。应用 SHALL 使用修改时间、符号链接、文件身份和清理前体积复核进行安全判断，不要求 `package.json` 或 lock 文件存在，允许计算聚合体积但不展示子文件，不设置体积阈值，并且不得自动选中该候选项。

#### Scenario: 项目依赖候选

- **WHEN** 扫描器在配置的项目目录中找到 `node_modules`
- **THEN** 创建一个代表整个目录的候选项
- **AND** 可以计算该目录的聚合体积
- **AND** 不展示或列出目录内的文件

#### Scenario: 依赖保护

- **WHEN** `node_modules` 是符号链接、扫描后身份发生变化或清理前体积发生变化
- **THEN** 应用将其标记为受保护或跳过
- **AND** 不选中该候选项

#### Scenario: 项目依赖时间范围

- **WHEN** 项目产物或 `node_modules` 所在项目目录在最近 30 天内有更新
- **THEN** 应用跳过该候选项
- **AND** 超过 30 天未更新的候选项进入待复核列表

#### Scenario: 可重建项目产物

- **WHEN** 扫描在配置项目根目录中发现已识别的依赖、构建、测试或工具产物目录
- **THEN** 应用将整个目录作为默认未选中的候选并计算聚合体积
- **AND** 命中该目录后不再向内发现嵌套候选
- **AND** 全局工具缓存不进入项目清理分组

#### Scenario: 依赖候选项展示

- **WHEN** 展示扫描到的 `node_modules` 候选项
- **THEN** 只显示聚合体积和路径
- **AND** 在用户明确确认前保持未选中

#### Scenario: 依赖移除

- **WHEN** 用户确认 `node_modules` 候选项
- **THEN** 将整个目录移入 macOS 废纸篓
- **AND** 不永久删除目录内的单个依赖

### Requirement: 清理任务选择

空闲界面 SHALL 提供一个主清理操作，并在主界面状态切换时保持圆形主操作的垂直位置一致。该操作 SHALL 启动统一扫描，覆盖安全清理、已卸载应用残留、项目产物和合并后的大文件扫描。空闲界面不得再提供独立的大文件扫描或开发清理主入口。

#### Scenario: 启动统一清理

- **WHEN** 用户点击“一键清理”
- **THEN** 应用启动统一的只读扫描
- **AND** 不要求用户先选择独立的清理类别

#### Scenario: 启动磁盘访问受限

- **WHEN** macOS 尚未授予 Spotless 完全磁盘访问权限
- **THEN** 统一扫描继续检查可读取的位置
- **AND** 同一主界面显示一条合并的权限提示，并提供前往系统设置的操作
- **AND** 权限提示使用“需要完全磁盘访问”和“开启后，扫描结果会更完整”的简短单行文案
- **AND** “去设置”操作保持统一高度和紧凑间距，不挤压提示文案
- **AND** “去设置”以纯文字操作展示，不额外显示图标
- **AND** 所有可用的界面操作在悬停时显示手形指针，禁用操作保持默认指针

#### Scenario: 空闲主操作布局

- **WHEN** 应用处于空闲状态
- **THEN** 顶部磁盘信息与圆形主操作之间有明确的垂直留白
- **AND** 圆形主操作与说明文字、权限提示之间保持舒适的垂直间距
- **AND** 圆球尺寸、主操作文案和清理行为保持不变

#### Scenario: 圆形主操作位置一致

- **WHEN** 应用在空闲、扫描、等待确认、清理中、完成或部分完成状态之间切换
- **THEN** 圆形主操作与顶部磁盘信息之间使用一致的垂直定位
- **AND** 工作状态动画不改变圆球中心位置
- **AND** 空闲和工作状态使用一致的圆球基础样式
- **AND** 悬停状态通过可感知但柔和的缩放和光晕反馈，正在扫描状态通过明显但克制的缩放和阴影呼吸反馈
- **AND** 上述视觉反馈不绘制突兀的轮廓线，也不改变圆球中心位置
- **AND** 工作状态的圆形主操作与 provider 状态面板之间保留稳定的视觉缓冲，阴影和缩放不侵入面板内容
- **AND** 圆球呼吸效果仅在正在扫描状态显示，清理执行、完成、部分完成和空闲状态不显示呼吸效果
- **AND** 弹出窗口在内容高度变化时使用窗口自身的尺寸过渡，不对内容树附加全局布局动画
- **AND** 扫描和清理进行中不显示尚未开始的 provider 占位内容，并关闭高频内容更新触发的窗口尺寸动画
- **AND** 进入扫描结果或完成状态时恢复窗口尺寸动画
- **AND** 圆球尺寸、文案和清理行为保持不变

#### Scenario: 主界面隐藏重复品牌标识

- **WHEN** 用户打开 Spotless 主界面
- **THEN** 顶部显示启动磁盘图标和可用空间信息
- **AND** 顶部不显示 `Spotless` 文字标识
- **AND** 菜单栏图标、应用名称和主清理操作保持不变

#### Scenario: 复核候选项

- **WHEN** 统一扫描发现需要确认的候选项
- **THEN** 同一主界面按类型分组展示候选项
- **AND** 不自动选中应用残留、项目依赖或大文件扫描候选项

#### Scenario: Provider 空结果状态

- **WHEN** provider 扫描结果为 0 项
- **THEN** provider 状态行使用正常完成图标，不使用感叹号图标
- **AND** provider 的状态行仍保留 0 项文案
- **AND** partial 且存在候选项时继续使用警示图标

#### Scenario: 过滤空清理候选

- **WHEN** 可清理文件或目录的实际大小明确为 0 KB
- **THEN** 应用不将其展示为可清理候选项
- **AND** 大小未知的内容仍可作为候选项展示

#### Scenario: 展示已选与总大小

- **WHEN** 候选列表展示“可清理项目”标题
- **THEN** 标题右侧显示当前已选候选项的大小和全部候选项的已知大小总和
- **AND** 两个大小值使用 `/` 分隔

#### Scenario: 限制可清理项目卡片高度

- **WHEN** 可清理候选项卡片展示
- **THEN** 卡片（包含标题和列表）最大高度为 `640pt`
- **AND** 超出卡片可用高度时只有列表内容在卡片内部滚动，不继续扩大主面板
- **AND** 卡片上方的扫描区域和下方的操作区不受该高度限制
- **AND** 当屏幕可用高度不足时，卡片上限随可用区域降低，主面板不超出屏幕可视区域

#### Scenario: 点击候选项名称选择

- **WHEN** 用户点击可选候选项的名称
- **THEN** 应用切换该候选项的选中状态
- **AND** 点击选择图标与点击名称使用相同的切换逻辑
- **AND** 点击路径、大小或行内空白不触发选择
- **AND** 已完成、受保护或其他不可选候选项不响应选择操作

#### Scenario: 清理执行期间保持操作按钮

- **WHEN** 用户点击“移到废纸篓”并进入清理执行状态
- **THEN** “移到废纸篓”按钮继续显示但处于禁用状态
- **AND** 圆球显示“正在清理”
- **AND** “完成”按钮继续显示但处于禁用状态，不可中断当前流程
- **AND** 操作区从左到右依次排列“移到废纸篓”和完成/取消，不增加额外的重新扫描入口
- **WHEN** 清理完成或部分完成
- **THEN** 圆球显示“清理完成”
- **AND** 完成操作恢复可用
- **AND** 候选项目列表继续保留在当前界面，不因状态切换重置
- **AND** 候选项目列表保持清理前的滚动位置

### Requirement: 刷新完全磁盘访问状态

应用 SHALL 在应用重新激活和面板重新打开时刷新完全磁盘访问状态，使权限提示反映最新系统设置。

#### Scenario: 从系统设置返回

- **WHEN** 用户从系统设置返回并使 Spotless 重新激活
- **THEN** 应用重新探测完全磁盘访问状态
- **AND** 仅更新权限状态和相关提示，不自动请求权限

#### Scenario: 重新打开面板

- **WHEN** 用户重新打开 Spotless 面板
- **THEN** 应用重新探测完全磁盘访问状态
- **AND** 只执行一次轻量只读检查，不改变扫描规则

### Requirement: 清理任务行为

应用 SHALL 保持扫描只读，绝不将清理作为扫描的副作用。扫描完成后，应用 SHALL 要求用户明确确认清理方案，才可以执行任何文件或目录操作。统一流程 SHALL 包含深度清理、应用和残留发现、缓存与服务刷新、项目产物，以及合并后的空间分析（安装包、压缩包、指定目录中的大文件和 Time Machine 检查）。缓存清理 SHALL 额外覆盖已配置的开发工具缓存以及多个受安全规则约束的临时目录。除 `~/Downloads`、`~/Desktop`、`~/Documents` 中普通文件大于 10 MB 的专门规则外，空间分析不设置通用固定体积阈值。

#### Scenario: 只读扫描

- **WHEN** 统一扫描完成并发现范围受限的安全缓存、日志或刷新候选项
- **THEN** 应用展示候选项但不改变文件系统
- **AND** 在确认前不执行任何候选项

#### Scenario: 启动磁盘分析

- **WHEN** 统一扫描分析本地启动磁盘
- **THEN** 报告总容量、可用空间和可测量的已占用空间
- **AND** 将外置、可移除、网络和受保护磁盘排除在启动磁盘大文件候选项之外
- **AND** 只保护系统 Photos.app、Music.app 及其明确关联的数据，不整目录排除用户的 `Pictures`、`Music` 和 `Movies`
- **AND** `Downloads`、`Desktop` 和 `Documents` 中逻辑大小大于 10 MB 的普通文件进入候选评估
- **AND** 安装包和压缩包等特殊文件保持现有候选规则
- **AND** 先完成路径、卷和保护边界判断再读取条目元数据，已读取的文件属性在同一次遍历中复用
- **AND** 标准目录优先处理，不能因全盘其它目录超时而跳过已经可访问的标准目录
- **AND** 元数据读取失败时报告部分扫描诊断，不静默丢弃整个分析结果
- **AND** 同一个文件通过硬链接出现多次时只计入一次空间统计和候选集合
- **AND** 在统一扫描中，空间分析只跳过缓存清理、项目清理和应用残留实际生成的候选路径及其子项，避免重复展示
- **AND** 前述 provider 因近期修改、归属不明确或读取失败没有生成候选时，空间分析仍可评估其中符合规则的文件
- **AND** 被前三类候选覆盖的路径仍计入空间统计，不因候选屏蔽而减少空间概览的可测量占用
- **AND** 不限制空间分析候选项数量，不新增空间概览或候选数量相关界面

#### Scenario: 空间分析部分完成但已有候选时显示可用状态

- **WHEN** 空间分析因受保护或不可读取路径被标记为部分完成
- **AND** 已经发现一个或多个可复核候选项
- **THEN** provider 状态行显示成功勾选和成功色
- **AND** 继续显示已有候选数量和实际大小
- **AND** 不改变其它 provider 的部分完成状态显示规则

#### Scenario: 系统应用关联媒体数据保持受保护

- **WHEN** 启动磁盘分析遇到系统 Photos.app、Music.app 或其稳定应用容器、图库和资料库数据
- **THEN** 应用在读取元数据前跳过这些路径，不创建可选择候选，也不进入可选遍历
- **AND** 这些子树的体积不计入可测量占用，只体现在总容量与可用空间的差额中
- **AND** 不因路径位于用户 `Pictures`、`Music` 或 `Movies` 目录就保护同目录下与系统应用无关的普通文件

#### Scenario: 类 bundle ID 的 .app 后缀数据目录不被整体排除

- **WHEN** 启动磁盘分析遇到用户目录下名称为类 bundle ID（多段点分隔）且以 `.app` 结尾的数据目录，如 `Library/Application Support/com.example.app`
- **THEN** 不将其作为应用包整体排除，正常进行空间统计与特殊文件候选评估
- **AND** `Example.app` 等非 bundle-ID 风格的 `.app` 名称仍按应用包排除，不作为普通文件扫描

#### Scenario: Time Machine 检查

- **WHEN** 统一扫描检查 Time Machine
- **THEN** 将快照状态和可用性作为分析信息报告
- **AND** 在执行任何快照维护操作前要求用户明确确认

#### Scenario: 没有可维护的本地快照

- **WHEN** `tmutil listlocalsnapshots /` 只返回任意格式的磁盘标题、系统管理快照或没有实际可维护的 Time Machine 快照记录
- **THEN** 空间分析不创建 Time Machine 快照候选项
- **AND** 保留“未发现本地快照”的扫描诊断
- **AND** 空间分析项目计数不因标题行或系统管理快照增加

#### Scenario: 存在可维护的本地快照

- **WHEN** `tmutil listlocalsnapshots /` 返回一个或多个 `com.apple.TimeMachine.*` 实际快照记录
- **THEN** 空间分析创建一个聚合的 Time Machine 维护候选项
- **AND** 该候选项保持待确认状态

#### Scenario: 项目产物

- **WHEN** 统一扫描发现已识别的项目产物
- **THEN** 报告其路径、类别以及可测量的体积
- **AND** 保护近期、不明确的项目，不允许选中
- **AND** 产物目录仅在名称命中且从父目录向上至扫描根的祖先链中存在项目特征标记（如 `.git`、`package.json`、`go.mod`、`Cargo.toml`、`Podfile`、`*.xcodeproj`）时生成候选

#### Scenario: 无项目标记的通用目录名不入选

- **WHEN** 扫描根下的目录名称命中 `build`、`dist`、`target` 等产物目录名，但其祖先链直到扫描根不存在任何项目特征标记
- **THEN** 不生成项目产物候选
- **AND** 该目录作为普通目录参与后续空间分析，不因名称被排除统计

#### Scenario: monorepo 深层产物目录命中上层标记

- **WHEN** 产物目录的父目录没有项目特征标记，但继续向上的祖先链中存在标记
- **THEN** 该产物目录仍进入项目产物候选评估，近期保护规则不变

#### Scenario: 扫描后候选项内容变化

- **WHEN** 用户确认清理后，候选文件或目录的身份或可测量体积与扫描时不同
- **THEN** 应用不移动或删除该候选项
- **AND** 将其报告为“扫描后内容已变化，请重新扫描后再清理”
- **AND** 部分清理结果仍然保留，不重复执行已经完成的候选项
- **AND** 用户点击“完成”返回空闲页后，可以从主清理入口重新开始统一扫描

#### Scenario: 路径策略校验失败

- **WHEN** 候选路径不在允许根目录、命中排除或保护规则、是符号链接或已不存在
- **THEN** 应用不移动或删除该候选项
- **AND** 使用对应的路径或安全校验原因报告失败

#### Scenario: 动态缓存目录

- **WHEN** DerivedData 等允许清理的缓存目录在扫描后继续被进程修改
- **THEN** 应用将其视为内容变化而不是非法路径
- **AND** 应用要求用户重新确认当前目录内容后再执行清理

### Requirement: 安全移除目标

应用 SHALL 将所有文件和目录移入 macOS 废纸篓，包括用户应用、残留、项目依赖、安装包、大文件、目录、系统缓存和旧日志。不得提供永久删除模式，并 SHALL 在确认前展示移除方式。

#### Scenario: 用户拥有的复核候选项

- **WHEN** 用户确认一个可处理的用户目录候选项
- **THEN** 应用将整个候选项移入 macOS 废纸篓
- **AND** 结果标记为移入废纸篓，而不是永久删除

#### Scenario: 需要权限的复核候选项

- **WHEN** 用户确认需要管理员权限的系统缓存或日志候选项
- **THEN** 应用通过受限的特权操作将整个候选项移入用户的 macOS 废纸篓
- **AND** 结果标记为移入废纸篓，而不是永久删除

### Requirement: 清理会话复用管理员授权

应用 SHALL 在一次清理会话内复用首次成功取得的管理员授权，不得按重试批次重复要求用户输入密码。授权会话只存在于内存中，并在清理会话结束时释放。

#### Scenario: 首次特权清理取得授权

- **WHEN** 用户首次执行包含需要管理员权限候选项的清理
- **THEN** 应用只请求一次管理员授权
- **AND** 所有当前批次的特权候选项继续使用同一授权上下文处理

#### Scenario: 清理会话内重试

- **WHEN** 首次清理完成后仍有可重试的候选项，且用户尚未点击“完成”、取消或退出应用
- **THEN** 后续点击“移到废纸篓”复用当前清理会话的授权上下文
- **AND** 不重复要求用户输入密码

#### Scenario: 清理会话结束释放授权

- **WHEN** 用户点击“完成”、取消清理、开始新的统一扫描或退出应用
- **THEN** 应用释放当前清理会话的授权上下文
- **AND** 不保存用户密码或持久化管理员授权

### Requirement: 进度和实时日志

主界面 SHALL 为发现和清理展示一条有序的进度流程，并提供范围受限的进度、取消操作、部分诊断和逐项结果，不得用无限增长的原始日志填满主视图。

#### Scenario: 统一扫描进度

- **WHEN** provider 正在运行
- **THEN** 界面显示当前 provider、已处理进度和整体完成状态
- **AND** 正在扫描的 provider 行右侧按 provider 独立显示实时已扫描文件数
- **AND** 该数量表示已经实际检查过的文件数，不使用目录数量或已发现的候选项目数代替
- **AND** provider 完成后才显示该分类最终候选数量和可测量体积
- **AND** 扫描进度事件按时间节流，并在 provider 完成时发送最终计数
- **AND** 统一扫描期间不逐项推送候选列表更新，扫描完成后一次性提交完整候选集合
- **AND** 当前操作只使用一个阶段提示或结果指示，不额外叠加 loading

#### Scenario: 取消操作

- **WHEN** 用户取消扫描或清理
- **THEN** 应用在安全范围内停止启动新的工作
- **AND** 保留已经完成的结果，并将剩余工作报告为已取消或未处理

#### Scenario: provider 部分完成

- **WHEN** provider 遇到超时或权限边界
- **THEN** 界面将其标记为部分完成或不可用
- **AND** 其他安全范围内的 provider 继续执行

### Requirement: 完成摘要

结果状态 SHALL 保留在主界面，并在候选列表中呈现已确认项目的逐项处理状态和仍待处理的候选项；清理摘要数据可以保留用于历史记录，但不得渲染为独立结果汇总。

#### Scenario: 确认后的清理结果

- **WHEN** 已确认的清理方案完成
- **THEN** 圆形主操作显示“清理完成”
- **AND** 已确认候选项在原列表行中显示对应的处理状态
- **AND** 不展示清理前后空间、分类统计或结果明细汇总

#### Scenario: 仍有候选项的结果

- **WHEN** 确认清理后仍有可处理候选项
- **THEN** 展示分组数量、可测量时的合计体积，以及展开后的路径
- **AND** 用户可以不离开主界面继续选择和确认

#### Scenario: 失败候选的信息展示

- **WHEN** 某个候选项清理失败
- **THEN** 原列表行显示失败状态和清理操作返回的失败原因
- **AND** 失败原因保持单行，超出宽度时在末尾显示省略号，悬停可以查看完整原因
- **AND** 候选路径保持单行，超出宽度时在末尾显示省略号，悬停可以查看完整路径

#### Scenario: 结果态继续选择候选项

- **WHEN** 用户在清理完成或部分完成后重新选择未处理候选项
- **THEN** 候选区标题右侧显示已选数量、候选总数和已选项目总大小
- **AND** 该选择摘要与等待确认状态保持一致，不显示已处理项目数量

#### Scenario: 空结果

- **WHEN** 统一扫描没有发现安全候选项或待复核候选项
- **THEN** 应用显示成功的空结果状态
- **AND** 用户可以从同一界面重新开始统一扫描

### Requirement: 扫描隐私与磁盘边界

应用 SHALL 只分析本地启动磁盘，排除外置、可移除和网络磁盘，保护系统及敏感路径，并在读取或测量照片、音乐应用图库的子项前跳过这些图库。

#### Scenario: 受保护的媒体图库

- **WHEN** 遍历到用户的 Pictures 或 Music 根目录、照片或音乐图库、任意应用包、Music.app 或 Apple Music 应用数据容器
- **THEN** Spotless 在资源测量前跳过该路径及其子项
- **AND** 不将访问该图库的授权作为清理前提

### Requirement: 主题色与应用图标保持一致

应用 SHALL 以 `#3FA796` 作为唯一主色，以 `#E8D9B5` 作为低频辅助色，并为失败状态提供低饱和暖砖红。面板边框和正文 SHALL 使用系统颜色，面板背景 SHALL 使用透明系统材质，避免多套强调色破坏整体层级，同时保留桌面环境色经过模糊后的自然透出。亮色外观下，面板 SHALL 在原生材质之上叠加唯一一层纯白低 alpha 提亮视图以提升白度，且 SHALL NOT 使用中性灰（如 `windowBackgroundColor`）作为根背景 tint；三个内容卡片 SHALL 直接在根面板毛玻璃之上叠加不透明度 `0.20` 的纯白 tint，不重复叠加 `thinMaterial`，边框使用 `Color.primary.opacity(0.2)` 以拉开与主面板的层次。暗色外观下，根面板 SHALL 沿用系统半透明玻璃，并在 macOS 26 及以上使用与亮色同一层级的应用侧表面叠加机制叠加低 alpha 中性深色层；该层不得是纯白提亮层或不透明实色底层，且 SHALL 保留桌面颜色经模糊后的自然透出。暗色内容卡片 SHALL 直接在根面板毛玻璃之上保留 0.06 低 alpha 白色提亮，不重复叠加 `thinMaterial`，边框沿用 `Color.primary.opacity(0.07)`，以保留模糊透底。品牌色、辅助色、失败色、系统文字色、按钮、布局 SHALL 保持现有设置。面板内两套 pill 按钮 SHALL 共用同一套尺寸与状态量，禁用填充 SHALL 使用与次按钮使能态同源的中性 tint，且 SHALL NOT 借用描边色。

#### Scenario: 主操作使用品牌色

- **WHEN** 用户查看主操作、一般强调或扫描中的进度状态
- **THEN** 相关颜色使用 `#3FA796`
- **AND** 主操作前景使用白色，保证小字号文字与品牌色按钮背景形成清晰对比
- **AND** 圆形主操作内部文字使用白色，保证两个主操作的前景色视觉一致

#### Scenario: 主操作按钮保持统一

- **WHEN** 用户查看圆形主操作或“移到废纸篓”按钮
- **THEN** 两者使用同一 `#3FA796` 主操作背景
- **AND** 两者使用同一白色前景
- **AND** 完成和取消按钮继续使用中性次要样式

#### Scenario: 禁用与按下状态共用同一套量

- **WHEN** 用户查看“移到废纸篓”或“取消 / 完成”按钮
- **THEN** 两者使用同一圆角、同一字号和同一按下透明度
- **WHEN** 任一按钮处于禁用状态
- **THEN** 其填充使用与次按钮使能态同源的中性 tint，不使用描边色
- **AND** 禁用按钮的视觉重量不高于同一行内可点的次按钮
- **AND** 禁用文字使用系统次要文本色

#### Scenario: 状态颜色保持语义区分

- **WHEN** 界面展示成功、警告或失败状态
- **THEN** 成功、选中和正在扫描使用 `#3FA796`
- **AND** 取消、受保护说明和低风险 provider partial 使用系统次要文本色
- **AND** 候选项部分完成状态继续使用辅助色 `#E8D9B5`，仅用于低频状态图标和说明
- **AND** 失败使用低饱和暖砖红色

#### Scenario: 菜单栏图标保持系统模板行为

- **WHEN** macOS 在菜单栏显示 Spotless 图标
- **THEN** 图标继续使用 template rendering 的单色行为
- **AND** 主题色调整不改变菜单栏图标的系统适配方式

#### Scenario: App Icon 使用当前主题色

- **WHEN** 用户查看 Spotless 的 App Icon
- **THEN** 圆角方形背景使用当前主题色 `#3FA796`
- **AND** 米白色六边形环、内外六边形比例和四角透明区域保持不变
- **AND** `AppIcon.appiconset` 的所有尺寸使用一致的主题色与几何结构
- **AND** 备用 `icon-source.svg` 使用相同的主题色、六边形结构和透明圆角
- **AND** 菜单栏图标继续保持黑色 template 资源，不因 App Icon 配色同步而改变

#### Scenario: 清理成功结果保持简洁

- **WHEN** 候选项清理成功并进入 `movedToTrash` 或 `removed` 状态
- **THEN** 候选行保留成功图标
- **AND** 不在路径下方重复显示“已移到废纸篓”或“已清理”等成功结果文案
- **WHEN** 候选项失败、跳过或取消
- **THEN** 候选行继续显示对应的结果文案，失败时优先显示具体失败消息

#### Scenario: 主题色与毛玻璃层次保持协调

- **WHEN** 用户查看主操作、成功、警告或失败状态
- **THEN** 主操作、品牌强调、成功、选中和正在扫描使用 `#3FA796`
- **AND** 辅助色 `#E8D9B5` 保持现有用途，只用于低频候选项部分完成状态，不作为常规正文颜色
- **AND** 失败使用低饱和暖砖红色
- **WHEN** 用户查看主弹出层或内容面板
- **THEN** 界面继续使用系统毛玻璃材质
- **AND** 桌面颜色可以经过模糊后自然透出，不固定为浅蓝、浅灰绿或其他品牌底色
- **AND** 不使用不透明纯色背景覆盖主弹出层的系统材质
- **AND** 三个内容面板保留现有内容分组、圆角和低对比度描边
- **AND** 内容区域不使用固定不透明主题色作为底层
- **AND** 主界面使用无边框面板和单层系统透明材质，不依赖 `NSPopover` 默认表面
- **AND** 面板、材质视图、表面叠加层、HostingView 和内容窗口使用同一个动态系统外观
- **AND** SwiftUI 根内容保持透明，不重复承载 AppKit 材质或自定义不透明根背景
- **AND** 面板内唯一的原生背景视图在 macOS 26 及以上使用系统组件 `NSGlassEffectView`（系统菜单同款渲染），更低版本使用 `.menu` 材质；内容始终以约束贴在表面视图上，且表面图层带圆角遮罩，避免窗口阴影按方形绘制
- **AND** 亮色外观下，在该材质之上叠加唯一一层纯白低 alpha 提亮视图；macOS 26 使用较轻的中性 `NSColor.white` 雾化比例，较早系统沿用冷白提亮色；不使用 `windowBackgroundColor` 等中性灰 tint
- **AND** 亮色外观下三个内容卡片直接叠加不透明度 `0.20` 的纯白 tint，不重复使用 `thinMaterial`，边框使用 `Color.primary.opacity(0.2)`
- **AND** 可清理项目卡片标题与列表之间的分隔线在亮色主题下使用 `0.25` 不透明度，暗色主题保持 `0.45`，继续区分标题区和列表区
- **AND** 暗色外观下根面板使用与亮色相同层级的单一应用侧表面叠加机制，叠加层为低 alpha 中性深色，不使用纯白提亮或不透明实色底层，并保留系统玻璃的桌面模糊透出
- **AND** 暗色内容卡片直接在根面板毛玻璃之上叠加 0.06 低 alpha 白色提亮，不重复使用 `thinMaterial`，保留根面板的透底模糊
- **AND** 品牌色、辅助色、失败色、系统文字色、按钮、边框和布局保持现有设置
- **AND** 面板表面在彩色或深色桌面下应读得出背景的冷暖色偏，而不是恒定的中性白（指亮色外观）
- **AND** HostingView 和面板内容窗口保持透明，实际模糊由单层 AppKit 材质提供，SwiftUI 内容只叠加必要的透明或半透明层
- **AND** 圆球下方的扫描提示文案采用无句号的短语形式，中英文保持一致
- **AND** 扫描阶段事件更新圆球下方的当前阶段提示，高层阶段消息不会因 provider 状态切换被直接丢弃
- **AND** 缓存扫描阶段提示使用“正在扫描缓存”，与“缓存清理” provider 名称保持一致
- **AND** 扫描提示使用直接、易读的短句，包括“正在准备扫描”“正在扫描大文件”“正在扫描启动磁盘目录”和“扫描已部分完成”
- **AND** 缓存、项目和应用 provider 的扫描计数更新复用详细提示，不显示同义重复的阶段文案
- **AND** 项目 provider 详细提示使用“正在查找超过 30 天未更新的项目产物”，不展示 `node_modules` 等内部实现名称
- **AND** 圆球下方提示使用系统次要文字颜色，与权限卡片说明保持一致

#### Scenario: 清理流程中的面板保持常驻

- **WHEN** 应用处于 `scanning`、`awaitingConfirmation`、`applying`、`completed` 或 `partial` 状态
- **THEN** 用户点击面板和菜单栏图标之外的区域时，面板保持可见
- **WHEN** 应用处于 `idle` 状态
- **THEN** 用户点击面板之外的区域时，面板可以关闭

#### Scenario: 跟随系统主题在初始化时继承系统外观

- **WHEN** 用户选择“跟随系统”并启动应用
- **THEN** App、面板、材质视图、HostingView 和 SwiftUI 根视图不设置固定亮色或暗色外观覆盖
- **AND** 界面使用 macOS 当前 effective appearance，而不是沿用上一次手动主题的外观
- **WHEN** 用户在应用运行期间切换 macOS 外观
- **THEN** 面板和内容视图继续跟随系统外观更新

#### Scenario: 权限提示使用中性信息层级

- **WHEN** 用户查看完全磁盘访问权限提示
- **THEN** 权限提示使用 `lock.shield` 图标并采用 `#3FA796`
- **AND** “去设置”操作使用 `#3FA796`
- **AND** “去设置”右侧不显示重新检查图标
- **AND** 权限提示整体不使用警告色作为主要前景色
- **AND** 权限提示、扫描进度和可清理项目面板使用同一套透明材质层级
- **AND** 低风险 provider partial、取消和受保护说明使用系统次要文本色
- **AND** 候选项部分完成状态继续使用辅助色 `#E8D9B5`

### Requirement: 透明毛玻璃应用背景

应用 SHALL 使用与 macOS 输入法菜单相近的透明毛玻璃背景。背景需要保留桌面环境色的柔和透出和模糊效果，不得通过固定浅蓝色或其他不透明主题色替代系统材质。参考图只约束透明材质的视觉表现，不约束应用内文字、菜单项或布局。

#### Scenario: 桌面背景能够柔和透出

- **WHEN** 用户在白色、蓝色或其他彩色桌面背景上打开主弹出面板
- **THEN** 主弹出面板能够观察到桌面环境色的变化
- **AND** 桌面图案经过毛玻璃模糊，不以清晰细节穿透面板
- **AND** 面板不会固定呈现浅蓝或浅灰绿

#### Scenario: 内容面板保持整体通透

- **WHEN** 用户查看权限提示、扫描进度或可清理项目区域
- **THEN** 内容面板使用透明或半透明背景，根面板继续由系统材质提供模糊
- **AND** 内容区域与面板边缘之间不出现明显的不透明色块断层
- **AND** 面板通过背景透明度、圆角和边框维持内容层级

#### Scenario: 明暗主题同步

- **WHEN** 用户切换浅色、深色或跟随系统主题
- **THEN** 面板、HostingView、内容窗口和 SwiftUI 根视图使用同一个 effective appearance
- **AND** 透明材质自动采用对应主题的亮度与对比度
- **AND** 正文、按钮和候选项在不同桌面背景下保持可读
